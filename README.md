## Цель работы

Научиться проектировать и реализовывать сложные бизнес-операции с участием нескольких связанных сущностей, создавать интерактивные формы с динамической загрузкой данных, реализовывать проверки на стороне сервера с учётом конкурентного доступа, а также формировать пользовательские отчёты.

## Задачи

1. Создать страницу бронирования с динамической подгрузкой специалистов и временных слотов в зависимости от выбранной услуги (объекта) и даты.
2. Реализовать управление записями (список с фильтрацией, изменение статуса через AJAX, перенос времени с освобождением старого слота).
3. Обеспечить защиту от конкурентных бронирований (повторная проверка слота перед вставкой, транзакции).
4. Разработать страницу отчётов с ежедневной сводкой, рейтингом специалистов и отменёнными записями, а также экспорт в CSV.
5. Провести функциональное тестирование и исправление ошибок.

## Ход работы

### 1. Доработка базы данных
В таблицу `appointments` добавлены поля для хранения даты и времени (`date_time`), статуса.  
Создана таблица `appointment_log` для журналирования изменений статуса и переносов.  
В таблицу `objects` добавлено поле `duration` (длительность показа в минутах) для расчёта слотов.

### 2. Реализация зависимых выпадающих списков и выбора слотов
- **Выбор объекта** → динамическая загрузка специалистов (через `fetch` к эндпоинту, возвращающему JSON-список специалистов).  
- **Выбор специалиста и даты** → AJAX-запрос к `get_available_slots.php`, который вычисляет свободные интервалы с учётом рабочих часов (9:00–18:00, обед 13:00–14:00), длительности услуги и уже занятых слотов.  
- Слоты отображаются в виде радиокнопок, при выборе заполняется скрытое поле `date_time`.  
- Кнопка «Создать запись» активируется только после выбора слота.

### 3. Серверная проверка и защита от конкурентного бронирования
Перед вставкой записи в транзакции с уровнем изоляции `SERIALIZABLE` (в коде использована транзакция с явной проверкой) выполняется `SELECT COUNT(*)` на наличие уже существующей записи с тем же специалистом и временем. Если слот занят, выбрасывается исключение с понятным сообщением.

### 4. Управление записями
- Список записей с фильтрами по диапазону дат, статусу, специалисту, поиску по клиенту. Пагинация — 20 записей на страницу.  
- Статус отображается цветным индикатором.  
- Кнопки изменения статуса (подтвердить, отменить, завершить) отправляют AJAX-запрос к методу `changeStatus` без перезагрузки страницы.  
- Перенос записи: отдельная форма с выбором новой даты и загрузкой доступных слотов для текущего специалиста и объекта. После переноса старое время освобождается, новое занимается.

### 5. Отчёты
- Ежедневная сводка за месяц (количество записей, выручка).  
- Рейтинг специалистов по количеству записей и выручке за период.  
- Отменённые записи по дням.  
- Каждый отчёт можно экспортировать в CSV.

### 6. Тестирование и исправление ошибок
Основная проблема на этапе внедрения — несоответствие имён столбцов в коде и базе данных (использовалось `appointment_datetime` вместо реального `date_time`). После замены всех вхождений ошибка была устранена.  
Также был добавлен метод `clientHasBookingOnDate` в репозиторий для проверки дублирования клиента в тот же день.

## Контрольный вопрос: Какие трудности возникли при реализации зависимых выпадающих списков (услуга → специалист → слоты)?

**Ответ:**  
При реализации цепочки «услуга → специалист → доступные слоты» основными трудностями были:

1. **Синхронизация клиентской и серверной логики.** После выбора услуги необходимо динамически загружать список специалистов, но в предметной области «недвижимость» любой специалист может проводить показ любого объекта, поэтому первоначально цепочка «услуга → специалист» была избыточной. Однако для соблюдения требований был реализован запрос к серверу, который возвращал всех специалистов (в дальнейшем может быть доработан под реальную специализацию).

2. **Расчёт временных слотов с учётом длительности услуги и обеденного перерыва.** Потребовалось точно вычислять пересечения с уже занятыми интервалами, при этом длительность занятого слота ранее не хранилась в таблице `appointments` (все записи имели стандартную длительность 60 минут). Решено добавлением поля `duration` в таблицу объектов и использованием этого значения при построении сетки слотов. Для универсальности шаг сетки был установлен в 30 минут, но слот отображается только если весь интервал свободен.

3. **Обработка граничных условий обеденного перерыва.** Слот не должен начинаться в перерыв или пересекаться с ним. Реализована проверка: если начало слота попадает в диапазон обеда или его окончание заходит на обед, такой слот исключается.

4. **Клиентская активация кнопки отправки.** Кнопка «Создать запись» должна быть неактивна до тех пор, пока пользователь не выбрал все обязательные поля и конкретный слот. Это потребовало аккуратного управления состоянием через JavaScript-обработчики на изменение каждого зависимого элемента.

5. **Конкурентный доступ.** Даже после выбора слота на клиенте, к моменту отправки формы слот мог быть занят другим пользователем. Решено через транзакцию с повторной проверкой `SELECT COUNT(*)` непосредственно перед `INSERT`, с выводом понятного сообщения, если слот уже занят.

Все эти моменты удалось успешно решить, и форма работает интуитивно, без лишних перезагрузок страницы.
